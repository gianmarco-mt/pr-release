Setup per le PR

Azioni di rilascio

Quando una PR ha bisogno di un passo manuale per arrivare in un ambiente (uno script sul database, un backfill), l'agente di chi sviluppa lo scrive in un file dentro la repo. Al merge, l'agente di chi mergia lo segnala alla persona, che lo esegue o lo fa eseguire. Poi il passo viene smarcato con un commento sulla PR.

Il problema

Il passo manuale sta solo nel testo della PR

Capita che una PR richieda di lanciare uno script sul database, prima su dev e poi su prod. Se l'istruzione è scritta solo nella descrizione della PR, al merge nessuno la vede, e lo script viene lanciato solo quando qualcuno si accorge del problema.

E anche quando il passo viene fatto su dev, nessuno lo ricorda giorni dopo, quando lo stesso codice arriva su prod.

Cosa c'è nella repo

Una cartella e due righe

Il setup si installa una volta per repo: si aggiunge una cartella release-actions/ con un README di istruzioni, e due righe nell'AGENTS.md. Da quel momento, ogni PR che ha bisogno di un passo manuale aggiunge un file in quella cartella.

repo/
├── AGENTS.md                         ← + 2 righe: "se serve un passo manuale…", "se mergi…"
└── release-actions/
    ├── README.md                     ← le istruzioni per i due ruoli (installato una volta)
    ├── 482-recalculate-totals.md        ← creato dall'agente dello sviluppatore nella PR del task 482
    └── 495-backfill-history.md       ← creato nella PR del task 495

I file delle azioni non si modificano e non si cancellano: restano nella cartella. Chi mergia guarda solo quelli nuovi della PR che sta mergiando.

Passo per passo

Dalla PR a dev, poi a prod

Chi sviluppa · nella PR

L'agente crea il file dell'azione

Lo sviluppatore lavora al task 482 sul branch feat/482-recalculate-totals. La modifica richiede di ricalcolare i totali già salvati, quindi l'agente aggiunge alla PR il file release-actions/482-recalculate-totals.md:

Environments: dev, prod

What to do: run `python scripts/recalculate_totals.py` (dry run), check the count, then rerun with `--apply`.
When: after this PR is deployed there and the other repo has published config version 12.

Se la PR non ha bisogno di passi manuali, non si crea niente e per lo sviluppatore non cambia nulla.

Chi mergia · prima del merge su develop

L'agente avvisa, non esegue

Chi mergia chiede al suo agente di mergiare la PR. Prima del merge l'agente gli mostra i passi che la PR porta su develop, cioè su dev:

Agente di chi mergia

La PR #31 aggiunge un'azione di rilascio per dev e prod:

  • Cosa: ricalcolo dei totali, prima in prova e poi con --apply
  • Quando: dopo il deploy, e dopo che l'altra repo ha pubblicato la configurazione v12

Dopo il merge va fatta su dev. La lanci tu o la lancio io?

Se il file è incompleto, o se la PR sembra richiedere un passo che non ha dichiarato, l'agente lo segnala qui, prima del merge.

Chi mergia · dopo il merge e il deploy

La persona esegue, o lo chiede all'agente

Il passo lo fa la persona, oppure dice all'agente di farlo. L'agente non lancia niente di sua iniziativa.

Chi mergia · su GitHub

L'agente smarca con un commento sulla PR

Quando la persona dice che il passo è fatto, o che deve aspettare, l'agente scrive un commento sulla PR #31, quella che ha aggiunto il file. Il testo è fisso, così si ritrova con una ricerca:

Release action done on dev Release action pending on dev: waiting for config v12

Il file nella repo non viene toccato: niente caselle da spuntare, niente commit su develop.

Chi mergia · develop su main

Lo stesso, per prod, con tutte le PR insieme

Su prod non si porta una PR alla volta: si porta develop intero, con tutte le PR mergiate dall'ultimo rilascio. Funziona lo stesso. I file che develop ha nella cartella e main non ha ancora sono esattamente i passi da fare su prod, uno per ogni PR che ne aveva bisogno.

Agente di chi mergia

Portando develop su main arrivano su prod 2 azioni di rilascio:

  • 482-recalculate-totals.md (PR #31): ricalcolo dei totali, dopo la configurazione v12
  • 495-backfill-history.md (PR #36): backfill dello storico, subito dopo il deploy

Le altre PR del rilascio non hanno passi manuali. Le lanci tu o le lancio io?

Ogni passo si smarca sulla PR che ha aggiunto il suo file, non sulla PR di rilascio: Release action done on prod sulla #31, un altro sulla #36.

Così su ogni PR resta la storia del suo passo in tutti gli ambienti, dev e prod.

Il file dell'azione

Tre cose, niente di più

Nome
Il nome del branch senza il tipo: feat/482-recalculate-totals diventa 482-recalculate-totals.md.
Environments
In quali ambienti va fatto il passo, per esempio dev e prod.
What to do
I comandi esatti: prima la prova, poi l'esecuzione vera.
When
Cosa deve succedere prima, per esempio una configurazione che un'altra repo deve aver pubblicato.
  • Se il passo può farlo la pipeline, si automatizza e il file non serve.
  • Per cambiare un passo già fatto in un ambiente si aggiunge un file nuovo, invece di modificare quello vecchio.
